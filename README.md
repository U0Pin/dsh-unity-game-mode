# Unity 游戏开发模式（DSH bundle）

`dsh-unity-game-mode` 是一个 DSH bundle：注册一个新的对话模式 `unity游戏开发`，并为该模式提供一个**能扛住 Unity 重启**的 MCP 连接。

- 适用的 DSH 版本：`>=0.2.2-rc.1 <0.2.3-0`（写在 `package.json` 的 `engines.dsh`，版本不符时安装阶段即拒绝）。
- 仓库根目录**就是**插件包本身，可直接按 GitHub 仓库地址安装。
- 该模式是 DSH 自带 `ptc` 模式的一份拷贝，不是官方发行物；对外分发前请自行确认相关条款。

## 安装

前置条件（每位安装者自己的机器上）：

1. DSH 版本满足 `engines.dsh`。
2. 已在本机登录过 GitHub（git 凭据可用）——私有仓库的读取靠这台机器的登录状态，安装框里没有地方填密码。
3. Unity 侧装好并启动 `MCP for Unity`（监听 `127.0.0.1:8080`）；没启动也能装、能开对话，只是工具调用会报「编辑器未连接」。

安装步骤：

1. 打开 **添加插件**，在输入框填仓库地址并带上版本标签：

   ```
   https://github.com/<org>/<repo>#v1.1.0
   ```

   若安装器提示无法解析该地址，改用 `git+https://github.com/<org>/<repo>.git#v1.1.0`，或先不带标签安装、在结果里确认装到的版本。
2. 新建对话时在模式列表选 `unity游戏开发`。模式在对话开始后不能更换。

## 升级与卸载

- 第三方 bundle **不会自动更新**：升级 = 在插件管理里**先卸载**，再按新标签安装。
- 不填版本标签时装到的是默认分支最新代码，没有稳定版本可回退；分享时始终带标签。
- 卸载：插件管理里的 `remove_bundle`，目标 `dsh-unity-game-mode`。

## 这个模式包含什么

| 项 | 值 |
|---|---|
| 模式名 | `unity游戏开发` |
| preset id | `unity` |
| 组合 | 完整复制应用自带的 `ptc` 模式（24 个顶层子插件），末尾追加一条 Unity MCP 连接 |
| 顺序 | 5（排在自带四个模式之后） |
| 额外注册 | profile 级一行 `unity-mcp-bridge`（见下） |

只有选了这个模式的对话才会加载 Unity 工具；其它模式（`standard`/`ptc`/`minimal`/`cordis`）不受影响，也不会有那批 `mcp__unity__*` 工具（默认 30 个，激活全部分组后 49 个）。

## 为什么需要桥接

Unity 的 MCP 服务器（MCP for Unity）是一个随编辑器启停的 Python 进程。编辑器每次重启，服务器上**所有 MCP 会话都会消失**：带旧 `mcp-session-id` 的请求一律返回 `404 {"code": -32600, "message": "Session not found"}`。

DSH 的 MCP 客户端无法自己发现这件事：streamable-HTTP 传输在会话失效时不会触发 `onclose`，客户端仍然认为自己连着、工具仍然注册着，于是**后续每一次调用都失败**，只能靠重开对话恢复。

`bridge.js` 把会话的所有权拿到自己手里，对外提供一个「永远不会消失」的服务器：

```
DSH 会话 ──HTTP──▶ unity-mcp-bridge (127.0.0.1:18080/mcp) ──HTTP──▶ Unity MCP (127.0.0.1:8080/mcp)
```

- `initialize` 立即返回（编辑器在线时是真实服务器信息，离线时是上次缓存或占位信息），所以**编辑器关着也能开对话**，工具不会掉。
- 请求被转发；上游会话失效时桥接会重建会话并把该请求重发一次。这样做是安全的：会话失效意味着服务器在**执行之前**就拒绝了请求。
- `tools/list` 在编辑器离线时退回上次缓存；监督循环在编辑器回来后重新读取，**注入给模型的集合**有变化才向下游广播 `notifications/tools/list_changed`，DSH 会自动重新同步。
- 只注入已启用分组的工具：`manage_tools {action:"list_groups"}` 的 `enabled` 与工具自带的 `_meta.fastmcp.tags: ["group:<name>"]` 求交集，没有分组标签的工具（`manage_tools` 以及其它服务器元工具）永远保留。读不到分组状态时全放行，不会自锁。
- 监督循环在有下游会话时轮询上游，避免服务器 30 分钟的会话空闲超时。

## 使用

Unity 工具依赖编辑器侧的服务：`Window > MCP for Unity` 启动的 `http://127.0.0.1:8080`。服务没起来时桥接照样在线，工具仍在、调用会明确报「Unity 编辑器未连接」；编辑器打开后工具自动可用。

默认只把已启用分组（开箱只有 `core`，共 30 个工具）注入给模型，其余 19 个要先让 agent 调 `manage_tools` 激活对应分组。判定规则是「**只有服务器明确报告某组未启用时，才隐藏该组的工具**」：没有分组标签的工具、以及分组标签在 `list_groups` 里还没出现的新工具（例如后加的自定义工具集）一律照常注入，所以新增工具不需要重启桥接，也不会被永久藏掉。

两个注意点：分组状态是**上游会话级**的，而桥接只维持一条上游会话，所以同时开着多个 Unity 对话时它们共享分组；编辑器重启后分组回到默认，桥接会把可见集合同步回默认。

> 端口被占用是安全的：第二个 Host 会复用已经在跑的桥接实例；先启动的那个 Host 退出后，剩下的 Host 会在几秒内接管端口。

## 诊断

```
curl http://127.0.0.1:18080/health
```

返回上游是否连接、当前上游会话 id、工具数量（`tools` 为服务器列出的总数，`visible` 为实际注入的数量，`groups` 为已启用分组）、下游会话数与订阅流数量。Host 日志里 `unity-mcp-bridge:` 前缀的行记录连接、失效、重建与工具列表变化。

桥接把最近一次的服务器信息与工具列表缓存到 `~/.dsh/cache/unity-mcp-bridge.json`，所以冷启动时也能先注册工具。

## 可调参数

在 `cordis.patch.yml` 的 `unity-mcp-bridge` 行里：

| 键 | 默认 | 说明 |
|---|---|---|
| `port` / `host` | 18080 / 127.0.0.1 | 桥接监听地址 |
| `upstreamUrl` | `http://127.0.0.1:8080/mcp` | Unity MCP 服务器地址 |
| `callWaitMs` | 15000 | 编辑器离线时一次工具调用最多等多久再报错 |
| `pollUpMs` / `pollDownMs` | 15000 / 3000 | 上游在线 / 离线时的监督间隔 |
| `groupFilter` | `true` | 按分组启用状态过滤注入的工具；`false` 时退回旧行为（全部注入） |
| `groupStateMs` | 15000 | 分组状态的缓存时长；工具列表变动时会强制重读 |

改端口时记得同时改 preset 里 `unity-mcp` 行的 `url`。

## 维护

- **仓库根目录即包**：`files` 白名单决定发出去的内容，`test/`、`README.md` 属于仓库本身，不随包分发。
- 模式不支持继承：`cordis.patch.yml` 里的子插件清单是 `ptc` 的一份拷贝，应用升级后不会自动跟随上游，需要手动同步并升包版本。
- 自检：`npm test`（先跑插件契约测试，再跑桥接自测；Unity 场景只在本机 `8080` 可用时执行），也可以分开跑 `node test/plugin-contract.test.mjs` 和 `node test/bridge.test.mjs`。
- 本机开发可用「本地目录」安装（链接安装，改动 `cordis.patch.yml` 后需先卸载再安装；`index.js`/`bridge.js` 的内容改动只需重启 Host）。
- 改完 `cordis.patch.yml` 后需要先卸载再安装（链接安装的目录改动不会自动重载组合）。

## 发版

1. 改 `package.json` 的版本号，并更新 `CHANGELOG.md`。
2. 本机 `npm test` 通过后提交、推送到 `main`。
3. 打标签并推送：`git tag v<version> && git push --tags`。
4. 让队友卸载旧版，再按新标签安装。
